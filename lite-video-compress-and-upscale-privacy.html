2. Core Architectural Manifesto: Local-First Computing

Lite Video Compress and Upscale was conceived with a strict hardware-isolated architectural philosophy. In contrast to cloud-based video converters that demand gigabytes of bandwidth and expose personal recordings to third-party servers, our application executes all multimedia computation locally:

  • Hardware Acceleration (MediaCodec & NPU): We invoke native Android C++ / NDK hardware acceleration pipelines directly via MediaCodec, Android Media3 Transformer, and on-device neural acceleration runtimes.
  • No Middleman Proxy: The application does not maintain an intermediate web API, backend processing gateway, or media queue in the cloud.
  • Ephemeral Frame Buffering: Individual frames unpacked during compression and super-resolution upscaling reside temporarily in volatile random-access memory (RAM) and are discarded immediately upon encoding.

3. Information We Process (On-Device Operations)

All multimedia computation takes place within your device's isolated application sandbox:

🎬 A. User-Selected Video & Audio Files

  • Input Handling: When you tap to compress or upscale a video, the application reads the file via Android's native system file picker or Scoped Storage content URI.
  • Processing Operations: The engine parses container metadata (resolution, frame rate, duration, container format, video codec like H.264/AVC, H.265/HEVC, AV1, audio tracks, sample rate) to compute mathematical compression ratios and upscale scaling matrices.
  • Zero Remote Transmission: Media streams are decoded, transformed, and re-encoded locally. No raw videos, extracted frames, or audio streams are ever uploaded, transmitted, or cloned to any cloud server.

📁 B. Processed Media Output & Storage Directory

Exported media files are written directly into standard public scoped storage using Android MediaStore APIs under the designated studio directory:

/storage/emulated/0/Movies/Lite Video Compress and Upscale/

Once written, these files are completely under your ownership and can be shared, moved, backed up, or deleted using any system file manager.

🗄️ C. Local Compression History & Statistics

To enable you to compare file size savings (e.g., original vs. compressed size, bitrate reduction percentages, and completion timestamps), the application logs these metrics in an on-device local Room SQLite Database. This database is sandboxed in private internal memory and is never synchronized with remote servers.

⚙️ D. User Configuration & Performance Preferences

Your preferred compression presets, target file sizes (KB/MB), CRF values, audio bitrates, upscaling factors (2x, 4x), hardware encoder preferences, and theme selections are stored on-device using Android DataStore Preferences.

7. Data Security, Retention & Erasure

  • Zero Cloud Footprint: Since we do not transmit video files or user logs to remote servers, there is no centralized database vulnerable to data breaches.
  • Volatile Memory Hygiene: Decompressed video frames used by the AI upscaler and compression algorithms are allocated in volatile RAM and immediately garbage-collected upon pipeline completion.
  • One-Tap Local Erasure: You can purge your entire compression history log and clear temporary cache files at any moment directly within the in-app Settings menu.
  • Full OS Uninstallation: Uninstalling the application automatically deletes all internal app sandbox data, Room database files, and DataStore preferences from physical flash memory.
